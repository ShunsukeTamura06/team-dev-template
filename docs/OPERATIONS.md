# 運用手順書

導入が終わった後の、日々の使い方です。導入の手順は [ROLLOUT.md](ROLLOUT.md) を参照してください。

## ツールを改修する

**ツールを改修する人が**、毎回この流れで行います。担当外のツールでも同じです。

1. **改修する人が**、ツールのリポジトリで main を最新にし、作業用のブランチを作る

   ```
   git switch main
   git pull
   git switch -c <ブランチ名>        (例: fix-threshold)
   ```

2. **改修する人が**、Claude Code を起動して改修する。チームルール(AGENTS.md)とツールの業務文脈(README.md)は、Claude Code が自動で読み込む
   - 担当外のツールを初めて触るときは、最初に `/handover` を実行して、ツールの説明と作者への質問リストを出してもらう
3. **改修する人が**、仕様・設定値・入出力を変えた場合は、`/update-context` で README を更新する
4. **改修する人が**、`/self-review` を実行し、指摘があれば直す
5. **改修する人が**、commit・push し、MR を作る。MR の説明欄には、テンプレート(何のための変更か・確認したこと・高リスクかどうか)が自動で入るので、埋める
6. **改修する人が**、MR画面で CI(`lint`・`test`)の結果と、AIレビューのコメントを確認する
   - AIレビューの指摘のうち、直すべきものは直して push し直す(push すると CI と AIレビューがもう一度動く)
   - 直さない指摘は、そのコメントに理由を一言返信する
7. MR の説明欄の「高リスク」に1つでもチェックが付く場合は、**改修する人が**チーフにレビューを依頼し、**チーフが**承認してからマージする。それ以外は、**改修する人が**自分でマージする

## 新しいツールを作る

1. **作る人が**、社内GitLabで `team-dev-template` を開き、右上の **Code → Download source code → zip** でダウンロードして展開する
2. **作る人が**、展開したフォルダの名前をツール名に変え、`admin/` フォルダと `docs/` フォルダを削除する(導入・管理用の資料なので、ツールには不要)
3. **作る人が**、[ROLLOUT.md の 1-2・1-3](ROLLOUT.md#1-2-社内gitlabにプロジェクトを作る) と同じ手順で、ツール名のプロジェクトを作って push する
4. **作る人が**、Claude Code を起動し、作りたいものを伝える。最初に README の「目的」「業務背景」を一緒に埋め、`app/` のサンプルを実際の処理に置き換えていく
5. **推進担当が**、[ROLLOUT.md の 4-3](ROLLOUT.md#4-3-main-ブランチを保護する) の手順で、新しいプロジェクトを `admin/projects.txt` に追加し、main ブランチを保護する

## チーム共通ルールを変える

ルール(`AGENTS.md`)の正本は `team-dev-template` にあり、各ツールにはその写しがあります。
ルールを変えるときは、必ず正本を先に変えてから、各ツールに配ります。各ツールの `AGENTS.md` を直接書き換えると、ツールごとにルールがずれていきます。

### ルールを変えるきっかけ

| こんなとき | 変えるもの |
|---|---|
| AIレビューが的外れな指摘を繰り返す | `AGENTS.md` の「AIレビュアーへ」、または `.pr_agent.toml` |
| AIレビューが見逃した問題を人が見つけた | `AGENTS.md` にルールを1つ足す |
| 担当外のツールを触って困った | 困ったことが全ツール共通なら `AGENTS.md`、そのツールだけなら、そのツールの README |
| 守られていない、意味のないルールがある | `AGENTS.md` から削る |

### 手順

1. **ルールを変えたい人が**、`team-dev-template` で `AGENTS.md`(または `.pr_agent.toml`)を変える MR を出し、MR の説明欄に「何が起きたから変えるのか」を書く
2. **チーフが**、MR を確認してマージする。ルールが10個前後を大きく超えるときは、代わりに削るルールが無いかを検討する
3. **推進担当が**、`team-dev-template` のフォルダで次を実行し、各ツールに更新の MR を自動で作る

   ```
   git pull
   $env:GITLAB_URL = "https://gitlab.example.local"
   $env:GITLAB_TOKEN = "glpat-..."
   python admin/gitlab_admin.py sync-rules --dry-run     # 変わるツールとファイルを確認する
   python admin/gitlab_admin.py sync-rules               # 各ツールに MR を作る
   ```

4. **各ツール作者が**、自分のツールに届いた「チーム共通ルールを最新版に更新」の MR を確認してマージする

`sync-rules` が配るのは `AGENTS.md` と `.pr_agent.toml` だけです。`.gitlab-ci.yml` や `.claude/` を変えたときは、`--file` で配るファイルを指定します(例:`--file .gitlab-ci.yml`)。ただし、ツールごとに `.gitlab-ci.yml` を書き換えている場合は上書きになるので、配る前に各ツール作者に確認してください。

## 定期的にやること

| 頻度 | 誰が | 何を |
|---|---|---|
| 月1回 | チーフ | `AGENTS.md` を見直し、守られていない・意味のないルールを削る |
| 月1回 | チーフ | AIレビューのコメントを数件読み、的外れな指摘が多ければ上の手順でルールを直す |
| 年1回(期限の1か月前) | 推進担当 | AIレビュー用トークン(`ai-review`)を作り直し、CI変数 `AI_REVIEW_GITLAB_TOKEN` を更新する |

## うまくいっているかの判断

AIレビューが動いていることではなく、次の状態になっているかで判断します。

- **担当外のツールの軽微な改修を、作者に聞かずにこなせたか**(Claude Code と README だけで)
- そのとき、作者に聞く必要があったことは README に追記されたか
