# 運用手順書

導入後の日々の作業と、変更が起きたときの作業をまとめたものです。
導入時に1回だけ行う作業は [ROLLOUT.md](ROLLOUT.md)、全体の考え方と変更の一覧は [DESIGN.md](DESIGN.md) を見てください。
人と言葉の呼び方は ROLLOUT.md の冒頭と同じです。

## 1. 日々の開発(メンバー)

ツールのリポジトリで、普段どおり Claude Code を使って開発します。チーム共通ルールは、Claude Code が起動時に自動で読み込みます。

| いつ | 誰が | 何をするか |
|---|---|---|
| 作業を始めるとき | 担当者 | `git switch main` → `git pull` → `git switch -c <作業内容がわかるブランチ名>` |
| 編集中 | (自動) | Claude Code が `.py` を編集するたびに、ruff で整形される |
| MR を作る前 | 担当者 | Claude Code で `/team:self-review` を実行し、指摘を直す。MR の説明の下書きも出る |
| 仕様・入出力を変えたとき | 担当者 | `/team:update-context` で README を更新する(同じ MR に含める) |
| MR を作ったあと | (自動) | CI が `lint`・`test`・`ai_review` を実行する |
| AI レビューのコメントが付いたら | 担当者 | 直すか、直さない理由を返信してからマージする |
| MR の「次のいずれかに該当するか」に該当があるとき | 担当者 | チーフにもレビューを依頼する |
| 担当を引き継ぐとき | 引き継ぐ人 | `/team:handover` で説明を作り、受け取る人と一緒に読む |

## 2. 新しいツールを作る

1. **担当者**:社内 GitLab の対象グループで、空のプロジェクトを作る(ROLLOUT.md 1-2 と同じ操作。名前はツール名)
2. **担当者**:自分の PC で `git clone <GitLab>/my-group/<プロジェクト名>.git` → そのフォルダで `claude` を起動 → `/team:new-tool`
3. **担当者**:Claude Code の質問に答え、最後に表示される手順で main に push する
4. **推進担当**:`python admin/gitlab_admin.py protect my-group/<プロジェクト名>`(ROLLOUT.md 5-4 と同じ)

## 3. チーム標準を変える(誰でも提案、チーフが承認)

チーム標準の変更は、すべて中央リポジトリ(`my-group/team-dev-template`)への MR で行います。**各ツールのリポジトリでの作業はありません。**

### 3-1. 共通の手順

1. **提案する人**:中央リポジトリの該当ファイルを Web IDE で開き(ファイルを開いて「編集」→「Web IDE で開く」)、変更する
2. **提案する人**:新しいブランチでコミットし、MR を作る。説明には「なぜ変えるか」を書く
3. **(自動)**:中央リポジトリの CI がテストを実行する。失敗したらマージできない
4. **チーフ**:MR を確認してマージする(中央リポジトリでマージできるのはチーフと推進担当だけ。ROLLOUT.md 1-6)
5. **(自動)**:各ツールの CI は次のパイプラインから、各自の Claude Code は次の起動から(自動更新の取り込み後)、新しい内容で動く

急いで全員に反映したいときは、チーフがチャット等で「`/plugin marketplace update team-dev` → `/reload-plugins` を実行してください」と連絡します。

### 3-2. 何を変えたいときに、どのファイルを変えるか

| 変えたいこと | 変えるファイル | 注意 |
|---|---|---|
| チーム共通ルール(追加・変更・削除) | `plugins/team/rules.md` | 10項目前後に保つ。8,000文字を超えると中央の CI が失敗する |
| AI レビューの観点 | `plugins/team/rules.md` の「AI レビュアーへ」 | |
| AI レビューの指摘の数・しきい値 | `pr-agent/pr_agent.toml` | |
| 書式チェックのルール | `plugins/team/ruff.toml` | 既存コードは、次に触ったファイルから順に対象になる |
| ruff・pytest のバージョン | `plugins/team/tool-versions.txt` | マージ後、各自の PC で起動時に警告が出る → 各自 `/team:setup` |
| Claude Code に読ませないパス | `plugins/team/protected-paths.txt` | |
| Claude Code のスキル(`/team:...`) | `plugins/team/skills/<名前>/SKILL.md` | 新しいスキルはフォルダを足すだけ |
| 全ツール共通の CI | `ci/python-tool.yml` | 1ツールで試してからマージするのが安全(下の 3-3)。`ruff.toml` などの変更も同じ方法で試せる |
| 新しいツールのひな形 | `plugins/team/templates/tool/` | 既存ツールには影響しない |

### 3-3. 共通 CI や設定ファイルの変更を、1つのツールで先に試す

1. **提案する人**:中央リポジトリで変更用のブランチ(例:`ci-try`)を作り、`ci/python-tool.yml` を変更して push する
2. **提案する人**:試すツールで作業ブランチを作り、`.gitlab-ci.yml` を一時的に次のように変えて MR を作る(`ref` を変えると CI の定義が、`TEAM_STANDARDS_REF` を変えると `rules.md`・`ruff.toml` などの設定ファイルが、`ci-try` のものになる)

   ```yaml
   include:
     - project: $TEAM_STANDARDS_PROJECT
       ref: ci-try
       file: /ci/python-tool.yml

   variables:
     TEAM_STANDARDS_REF: ci-try
   ```
3. **提案する人**:パイプラインの結果を確認したら、ツール側の MR は閉じる(マージしない)
4. **提案する人**:中央リポジトリで `ci-try` から MR を作り、チーフがマージする

### 3-4. 変更を取り消す

**チーフ**:中央リポジトリの該当 MR を開き、右上の「元に戻す(Revert)」を押して取り消しの MR を作り、マージします。

## 4. ツール固有のルールを変える(各ツールの担当者)

そのツールだけの例外や業務ルールは、そのツールの `README.md` の「このツール固有のルール」に書きます。チーム共通ルールより優先されます。
Claude Code(`@README.md` で読み込む)と AI レビュー(README を読む)の両方に効きます。

「どのツールにも当てはまる」と思ったら、README ではなく 3 の手順でチーム共通ルールへの追加を提案します。

## 5. 個人の好みを変える(本人)

自分の PC の `~/.claude/CLAUDE.md` に書きます。口調・説明の詳しさなど、コードの書き方に関わらないことだけにします。
コードの書き方に関わることは、3 か 4 の手順で提案します(個人の設定に書くと、他の人の Claude Code や AI レビューには効かないため)。

## 6. 定期的な作業

| 時期 | 誰が | 何をするか |
|---|---|---|
| ボット用トークンの期限の2週間前 | 推進担当 | ROLLOUT.md 3-1 でトークンを作り直し、CI 変数 `TEAM_BOT_TOKEN` の値を更新する(各ツールでの作業なし) |
| 月に1回 | チーフ | AI レビューの指摘で役に立たなかったもの・多すぎたものを振り返り、`rules.md` や `pr_agent.toml` を調整する |
| 四半期に1回 | チーフ | `rules.md` を読み直し、守られていない・不要になったルールを削る |
| PR-Agent が安定したら | 推進担当 | `ci/python-tool.yml` の `TEAM_PR_AGENT_IMAGE` を `latest` から特定のバージョンに固定する |

## 7. メンバーの参加・離任

| 出来事 | 誰が | 何をするか |
|---|---|---|
| 参加 | 推進担当 | 対象グループに Developer で追加する |
| 参加 | 本人 | ROLLOUT.md の段階0-5 と段階4 を行う |
| 離任 | 担当者 | 担当ツールごとに `/team:handover` で引き継ぐ。README の「担当」を更新する |
| 離任 | 推進担当 | 対象グループから外す。ボット用トークンを本人が作っていた場合は作り直す |

## 8. うまくいっているかの目安

- 担当者が不在のとき、別のメンバーが Claude Code と README だけで軽微な改修をできたか
- AI レビューの指摘のうち、実際に直したものの割合(低ければ `pr_agent.toml` や `rules.md` を調整する)
- 各ツールの README の「このツール固有のルール」「過去の障害・注意点」が更新されているか
