# チーム共通ルール

このファイルが、チーム共通ルールの正本です。
Claude Code にはプラグインがセッション開始時に読み込ませ、MR の AIレビューには CI が毎回読み込ませます。
各ツールのリポジトリには写しを置きません。変更は、このファイルを変える MR で行います。

ルールは10項目前後に保ち、運用しながら育てます(足したら、代わりに削れるものがないかも考える)。

## 優先順位

1. ツールの README の「このツール固有のルール」(書かれていれば、こちらが優先)
2. このチーム共通ルール

## 最優先の原則

**このコードは作成者以外が保守する。** 担当者が不在でも、他のメンバーが Claude Code と一緒に
このリポジトリを読めば、軽微な改修を自力でできる状態を保つ。

## 1. 構成

- `app/main.py`:入口。引数の処理と、各処理の呼び出し順だけを書く
- `app/data_io.py`:Excel・CSV・DB・フォルダなど外部との読み書き
- `app/logic.py`:業務判定・計算。**ファイルや DB に直接触らない**(テストしやすくするため)
- `app/config.py`:設定値の読み込み
- 業務ロジックが大きくなったら `app/logic/` に分割してよい。上の役割分担は崩さない
- 既存ツールは、改修のついでに少しずつこの構成に寄せればよい。一度に作り直さない

## 2. 設定値

- ファイルパス・フォルダ・接続先・閾値・日付をコードに直接書かない。`app/config.py` 経由で環境変数(`.env`)から読む
- 新しい設定値を足したら、`.env.example` と README の「環境変数」に追記する

## 3. 秘密情報とデータ

- パスワード・API キー・本番データ・顧客情報を Git に入れない(`.env`・`data/`・`output/` は Git 管理外)
- テストには `tests/fixtures/` に置いたダミーデータを使う

## 4. エラー処理

- 例外を握りつぶさない(`except: pass` や、ログを出さない `except Exception` は禁止)
- 業務上、処理を続行する場合は、理由と対象(ファイル名・行番号など)を WARNING ログに出す
- 入力ファイルが無い・列が足りない等は、原因が分かるメッセージで止める

## 5. ログ

- `print` ではなく `logging` を使う
- 最低限、処理の開始・終了・入力ファイル名・処理件数を INFO で出す

## 6. テスト

- `app/logic.py` の業務判定には pytest のテストを書く。境界値(ちょうど閾値、0件、空欄)を含める
- 不具合を直したら、その不具合を再現するテストを1つ足す

## 7. 読みやすさ

- 関数・変数に型ヒントを付ける
- 1関数はおおむね50行以内。超える場合は分割を検討する
- 業務用語の英語名は、README の「用語集」に合わせる。無ければ用語集に追加する

## 8. 業務文脈を残す

- コードから読み取れない「なぜ」(業務上の理由、依頼元、過去の障害)は README に書く
- 仕様・設定値・入出力を変えたら、README の該当箇所も同じ MR で更新する

## 9. 依存ライブラリ

- 追加したら `requirements.txt` に書き、理由を MR の説明に書く
- Windows でしか動かないライブラリには `; sys_platform == "win32"` を付ける(CI は Linux で動くため)

## 開発する AI エージェントへ

- 業務仕様が不明なときは推測で実装せず、ユーザーに質問する
- `data/` と `output/` の実データは読まない。動作確認は `tests/fixtures/` のダミーデータで行う
- MR を作る前に `/team:self-review` を実行する

## AI レビュアーへ

- 最重要の観点は「作成者以外がこのコードを保守できるか」。上のルールへの違反を、ルール番号を示して優先的に指摘する
- フォーマット・import 順・未使用変数は CI の ruff が検出するので指摘しない
- 業務仕様の正しさは判断できないため、仕様が不明確な箇所は「確認事項」として質問の形で書く
- 仕様・設定値・入出力が変わっているのに README が更新されていなければ指摘する
- 本番データ更新・DB 構造変更・外部システム接続・削除処理を含む場合は、冒頭でその旨を明記する
