# 既存ツールにチーム標準を導入する

ひな形は `${CLAUDE_PLUGIN_ROOT}/templates/tool/` にある。既存のコード(`app/` 以外の構成も含む)は作り直さない。

## 1. 準備

- 現在のフォルダが Git リポジトリで、`main` から切った作業ブランチにいることを確認する。`main` にいる場合は、`git switch -c adopt-team-standard` でブランチを作ってよいかユーザーに確認する

## 2. 既存の指示ファイルを仕分ける

既存の `CLAUDE.md`・`.claude/CLAUDE.md`・`AGENTS.md`・`CLAUDE.local.md` があれば読み、内容を次の3つに分けてユーザーに見せ、了承を得る。

| 分類 | 移し先 |
|---|---|
| どのツールにも当てはまる書き方のルール | ファイルには残さない。一覧にしてユーザーに渡す(ユーザーがチーフに渡し、チーフがチーム共通ルールに入れるか判断する) |
| このツール固有の情報・例外ルール | README の該当欄(「このツール固有のルール」「業務背景」など) |
| Claude Code だけに伝えたい操作上の注意 | 新しい CLAUDE.md の末尾 |

仕分けが終わったら、既存の `AGENTS.md` と `.claude/CLAUDE.md` は削除する(チーム共通ルールはプラグインが読み込むため不要)。`CLAUDE.local.md` は個人のファイルなので触らない。

## 3. ひな形のファイルを置く

| ひな形のファイル | 既存ファイルが無い場合 | 既存ファイルがある場合 |
|---|---|---|
| `.gitlab-ci.yml` | コピーする | 中身を見せてユーザーに相談する。独自のジョブがあれば、ひな形の `include` の下に残す |
| `CLAUDE.md` | コピーする | ひな形の内容に置き換え、手順2の「Claude Code への注意」を末尾に足す |
| `.gitlab/merge_request_templates/Default.md` | コピーする | 上書きせず、違いをユーザーに伝える |
| `.gitignore`・`.gitattributes` | コピーする | 足りない行だけを追加する |
| `.env.example` | コードが環境変数を使っている場合だけ、実際の変数名で作る | 変えない |

ひな形の `app/`・`tests/`・`requirements.txt` はコピーしない(サンプルなので)。
### 以前の方式で各リポジトリに写していた設定を外す

次があれば一覧にしてユーザーに見せ、了承を得てから削除する(チーム共通の設定は中央で一元管理するため。残すと中央の設定より優先され、チームの方針から外れる)。

| 見つかったもの | 対応 |
|---|---|
| `.pr_agent.toml` | 削除する。ツール固有の事情があれば README の「このツール固有のルール」に移す |
| `ruff.toml`・`.ruff.toml`、`pyproject.toml` の `[tool.ruff]` | 削除する(書式の設定はチーム共通のものを使う) |
| `.claude/settings.json` のうち、`team-dev` のマーケットプレイス・`team@team-dev` の有効化・`.env`/`data`/`output` の deny の項目 | その項目だけ削除する(プラグインと各自の PC 側で設定済み)。他の項目は残す。空になったらファイルごと削除する |
| ルールを各リポジトリに配るためのスクリプトや CI ジョブ | 削除する |

## 4. 依存ライブラリ

`requirements.txt` が無ければ、コードの import から作る。Windows でしか動かないライブラリ(`pywin32`、`xlwings` など)には `; sys_platform == "win32"` を付ける(CI は Linux で動くため)。

## 5. README

`/team:update-context` と同じ手順で README を作る(既存の README があれば、ひな形の見出し構成に沿って再構成する)。コードから分からないことは推測せず、ユーザーに質問する。

## 6. 確認

- 既存コード全体を ruff で整形しない(差分が巨大になるため。CI は MR で変更したファイルだけを確認するので、既存コードは触ったときに順に整う)
- `python -m pytest -q` を実行し、結果をユーザーに伝える(テストが無いことは問題としない)

## 7. 最後にまとめて表示する

- 変更・追加・削除したファイルの一覧
- 手順2の「どのツールにも当てはまる書き方のルール」の一覧(チーフに渡すもの)
- 次にユーザーがやること:commit・push して MR を作る → CI(`test`)が通ったらマージ → 推進担当に main ブランチの保護を依頼する
